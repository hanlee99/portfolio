핵심 문제 해결 경험

1. [비즈니스] 외부 API 데이터 매칭률 100% 달성

문제 KOBIS와 KMDB API의 제목 표기 차이로 매칭 실패. 초기 매칭률 90%. (예: "코렐라인: 비밀의 문" vs "코렐라인과 비밀의 문")
해결 1. 로그 분석으로 매칭 실패 패턴 발견
2. 2단계 매칭 전략: 정확 매칭 → 공백/특수문자 제거 LIKE 검색
3. 재개봉 영화("코렐라인", "가타카" 등) 별도 처리 로직 추가
결과: 매칭률 90% → 100% 달성

2. [N+1] 쿼리 최적화로 87% 성능 개선

문제 영화 상세 페이지에서 출연진마다 개별 쿼리 발생 (영화 1개 + 출연진 7명 = 8개 쿼리).
해결 1. Hibernate SQL 로그로 N+1 문제 확인
2. Fetch Join으로 Movie → MoviePerson → Person 한 번에 조회
3. DISTINCT로 중복 제거
4. 상황별 Repository 메서드 분리 (findById / findByIdWithPeople)
결과: 쿼리 수 8개 → 1개 (87% 감소)

3. [동시성] 다중 사용자 환경 데이터 정합성 보장

문제 여러 사용자가 동시에 영화 조회수를 업데이트할 때 Lost Update 발생 가능성. (예: 조회수 100 → 두 사용자 동시 접근 → 101이어야 하는데 100+1=101로만 저장)
고민한 선택지 1) Pessimistic Lock → DB 락으로 성능 저하
2) Optimistic Lock → 충돌 시 예외 발생, 재시도 필요
3) Optimistic Lock + @Retryable → 충돌 시 자동 재시도
해결 JPA @Version으로 Optimistic Lock 적용 + Spring @Retryable로 충돌 시 3회 재시도
결과: 동시성 환경에서 데이터 정합성 보장, 성능 저하 없음

4. [캐싱] Caffeine Cache로 API 응답속도 72% 개선

문제 KOBIS 외부 API 호출 시 평균 1.77초 소요. 박스오피스 데이터는 하루 단위 업데이트라 매번 호출 불필요.
해결 1. Caffeine Cache 적용 (인메모리 캐시)
2. 1시간 TTL 설정 (박스오피스 업데이트 주기 고려)
3. 날짜별 캐시 키 관리로 일별 데이터 분리
결과: 응답속도 1.77초 → 0.5초 (72% 개선), API 호출 80% 감소

5. [아키텍처] Adapter 패턴으로 외부 API 의존성 격리

문제 초기에 JsonNode로 외부 API 응답 직접 파싱 → 필드명 오타 위험, 타입 안정성 없음. 외부 API 스펙 변경 시 비즈니스 로직 전체 수정 필요.
해결 1. Adapter 패턴 도입: Service → Adapter → 외부 API
2. 외부 API DTO / 내부 Domain DTO 분리
3. Mapper 계층으로 변환 로직 격리
4. 3일간 전체 구조 리팩토링
결과: API 변경 시 Adapter만 수정, 비즈니스 로직 영향 없음

6. [CI/CD] GitHub Actions로 배포 자동화

문제 수동 배포 시 휴먼 에러 위험 (빌드 누락, 테스트 스킵 등). 배포할 때마다 SSH 접속 → 빌드 → 재시작 반복.
해결 1. GitHub Actions 워크플로우 구성
2. main 브랜치 push 시 자동 실행
3. 테스트 → 빌드 → EC2 배포 파이프라인 구축
결과: push만 하면 자동 배포, 휴먼 에러 제거

핵심 문제 해결 경험

1. AI가 모든 질문을 예측할 수 없는 문제

문제 "힌트 줘", "코드 리뷰해줘", "비슷한 문제 있어?" 등 다양한 질문에 대응 필요
선택지 버튼 UI → 자유 질문 불가 / 모든 데이터 프롬프트 → 토큰 낭비 / Function Calling 선택
해결 6개 함수 설계: 문제조회, 제출이력, 코드분석, 힌트제공, 유사문제, 통계
결과: AI가 맥락 파악 후 필요한 함수만 호출, 자연스러운 대화

2. 엔티티 분리 - 변경 주기/소유권이 다른 데이터 혼재

문제 문제 정보 + 제출 이력 + 사용자 메모가 한 엔티티에 혼재, 관리 어려움
분석 문제 정보(불변, 시스템) / 제출 이력(동기화, 시스템) / 사용자 메모(빈번, 사용자)
해결 3개 엔티티 분리: Problem(불변) / Submission(시스템) / ProblemUserData(사용자)
결과: 변경 영향 범위 최소화, 독립적 관리

3. N+1 쿼리 문제

문제 카테고리별 통계 조회 시 각 Problem마다 Submission 추가 조회
해결 Fetch Join으로 Problem + Submission 한 번에 조회
결과: 쿼리 367개 → 1개 (99% 감소)
