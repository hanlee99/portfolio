🏗️ 시스템 아키텍처

계층별 책임 분리 • Controller: HTTP 요청/응답
• Service: 비즈니스 로직 & 트랜잭션
• Adapter: 외부 API 격리
• Repository: 데이터 접근

핵심 설계 원칙 • Entity-DTO 분리로 계층간 결합도 최소화
• CQRS: 조회/수정 서비스 분리
• 의존성 역전: 외부 API → Adapter

🔧 핵심 문제 해결 경험

1. 외부 API 데이터 통합 및 매칭 전략 개선

🎯 문제 상황 • KOBIS API: 박스오피스 순위만 제공 (포스터/상세정보 없음)
• KMDB API: 영화 상세 정보 제공
• 두 API의 제목 표기 차이로 매칭 실패 (공백, 특수문자)
• 초기 매칭률 약 90% (재개봉 영화 등 예외 케이스 실패)
💡 해결 과정 1. Adapter 패턴으로 외부 API 의존성 격리
2. KMDB 데이터 선수집 (703건 저장)
3. 2단계 매칭 전략 도입:
• 1차: 정확 매칭 (title 완전 일치)
• 2차: 공백 제거 후 LIKE 검색
4. 매칭 실패 로깅으로 누락 케이스 발견
• 재개봉 영화 "코렐라인", "가타카" 등 DB 추가
• 매칭 로직 지속 개선
✅ 결과: 매칭률 90% → 거의 100% 달성, 재개봉 영화 등 예외 케이스 안정적 처리

2. N+1 쿼리 문제 해결

🎯 문제 상황 • 영화 상세 페이지 로딩 시 출연진마다 개별 쿼리 발생
• 영화 1개 + 출연진 7명 = 8개 쿼리 실행 (N+1 문제)
• Hibernate SQL 로그로 문제 확인
💡 해결 과정 1. fetch join으로 MovieEntity → MoviePersonEntity → PersonEntity 한 번에 조회
   • LEFT JOIN FETCH m.people mp LEFT JOIN FETCH mp.person
2. DISTINCT로 카르테시안 곱 중복 제거
3. 상황별 Repository 메서드 분리
   • findById(): 기본 조회
   • findByIdWithPeople(): 출연진 포함 조회
4. @Transactional(readOnly = true)로 조회 최적화
✅ 결과: 쿼리 수 8개 → 1개 (87% 감소), DB 왕복 횟수 최소화로 확장성 개선

🔧 핵심 문제 해결 경험 (계속)

3. 캐싱 전략 도입으로 API 호출 최적화

🎯 문제 상황 • KOBIS API 호출 시 평균 1.5-2초 소요
• 박스오피스 데이터는 하루 단위로 업데이트
• 같은 날짜 반복 조회 시 불필요한 API 호출 발생
💡 해결 과정 1. Spring Cache (@Cacheable) 적용
2. 날짜별 캐시 키 관리 (targetDt 기준)
3. 캐시 미스/히트 로깅으로 효과 측정
4. 1일 TTL 설정으로 데이터 최신성 유지
✅ 결과: 응답속도 1.77초 → 0.5초 (72% 개선), API 호출 80% 감소 (5회 중 1회만 호출)

4. JsonNode → DTO 구조 리팩토링

🎯 문제 상황 • JsonNode로 API 응답 직접 파싱
• 필드명 오타 위험, 타입 안정성 없음
• API 변경 시 영향 범위 파악 어려움
💡 해결 과정 1. 외부 API DTO / 내부 Entity 명확히 분리
2. Mapper 계층 도입으로 변환 로직 캡슐화
3. @JsonProperty로 API 필드명 매핑
4. 3일간 전체 구조 리팩토링
   • JsonNode 파싱 오류 위험 제거
   • API 변경 영향을 Adapter 계층으로 격리
   • 컴파일 타임 타입 체크로 안정성 확보
✅ 결과: 타입 안정성 확보, API 변경 영향 범위 최소화, 장기 유지보수성 향상

5. DB 구조 정규화 (영화-영화인 관계 분리)

🎯 문제 상황 • 초기: 영화 Entity에 출연진 정보 직접 저장
• 같은 배우가 여러 영화 출연 시 이름 중복 저장
• 영화 Entity 비대화 및 데이터 정합성 문제
💡 해결 과정 1. 영화-영화인 관계를 별도 테이블로 분리
2. Person Entity 생성 (영화인 정보 통합 관리)
3. MoviePerson Entity (중간 테이블) 생성
   • 역할(감독/배우), 배역명 정보 포함
4. 다대다 관계로 설계 변경
✅ 결과: 데이터 중복 제거, 영화인 정보 재사용 가능, DB 정규화 달성

🎯 주요 기술 선택

PostgreSQL 채택
  • 프로덕션 환경: Render 플랫폼 무료 지원
  • 안정성: H2 대비 안정적인 운영 환경
  • 성능: 복잡한 JOIN, LIKE 쿼리 최적화 우수
  • 확장성: 향후 Full-text search, JSONB 활용 가능
Service 계층 분리 (CQRS)
  • MovieService: 조회 전용 (readOnly = true)
  • MovieSyncService: 데이터 수정/동기화
  • 트랜잭션 최적화: 읽기 전용 최적화로 DB 부하 감소
  • 책임 분리: 단일 책임 원칙(SRP) 준수
Adapter Pattern 적용
  • 의존성 역전: Service → Adapter → 외부 API
  • 변경 격리: API 스펙 변경 시 Adapter만 수정
  • 테스트 용이: Mock Adapter로 외부 API 없이 테스트
  • 확장성: 새로운 API 추가 시 기존 코드 영향 최소화
Spring Cache 전략
  • 성과: 응답속도 1.77초 → 0.5초 (72% 개선)
  • 효율: API 호출 80% 감소 (5회 중 1회만 호출)
  • 전략: 날짜별 캐시 키, 1일 TTL
  • 비용: 외부 API 호출 비용 절감
